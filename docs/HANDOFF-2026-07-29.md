## 2. AI 추천 로직 (가장 최근 작업 — 이어서 할 가능성 높음)

### 구조

`app/services/recommendation_scoring.py` (백엔드, 신규 파일)

```
최종점수 = 관심도 0.35 + 자격 0.25 + 역량 0.20 + 규모 0.10 + 시의성 0.10
```

| 축 | 계산 |
|---|---|
| 관심도 | 스크랩·실적·품목·면허 텍스트를 임베딩 → OpenSearch kNN 유사도 × 신호 배수 |
| 자격 | `verdict`(가능 1.0 / 보완가능 0.6 / 확인필요 0.25) × 0.5 + 축 충족률 × 0.5 |
| 역량 | 회사 면허코드 ∩ 공고 요구코드 (집합 연산, 벡터 아님) |
| 규모 | 공고 예산 vs 회사 최대 실적 (0.3~2배 구간 만점) |
| 시의성 | D-3~14 만점, D-2 이하는 **감점**(준비 시간 부족) |

**예전 구조(사다리) 제거** — 스크랩 있으면 스크랩만 쓰던 방식. 스크랩 하나 지우면 추천이 통째로 뒤집혔다.

### 데이터 실측 (설계 근거)

```
required_licenses.code  21,776건 중 7,663건만 채워짐
  → code 없으면 name_raw 괄호에서 추출 ("소프트웨어사업자(1468)" → 1468)

후보 verdict 분포  확인필요 3,395 / 보완가능 604 / 가능 307
  → '가능'을 크게 가점해야 위로 올라옴
```

### 🔴 이어서 할 것

**① 가중치가 근거 없는 초기값이다**
0.35/0.25/... 는 감으로 정했다. **골든셋**(회사 3~5곳 × "이 공고가 상위에 와야 한다" 목록)을 만들어야 수치로 튜닝 가능. `recommendation_scoring.py` 상단 상수만 고치면 되게 모아뒀다.

**② 관심도 축만 정규화가 부실하다**
```python
min(1.0, max(0.0, raw)) * signal.weight   # ← 클리핑일 뿐 정규화 아님
```
OpenSearch kNN 점수는 코사인 유사도 그대로가 아니라 엔진 변환값이라, 1을 넘으면 뭉개지고 분포가 좁으면 상수처럼 작동한다. **나머지 4축은 0~1로 명시 계산했는데 이 축만 스케일이 불확실**하다.
→ 후보 집합 안에서 min-max 정규화로 바꿔야 가중치 비교가 의미를 갖는다. **골든셋 작업 전에 선행 권장.**

**③ 논의하다 만 것 — "조건 없는 공고"를 `제한없음` 태그로**

실측 결과:
```
확인필요 2,961건
├─ 판정축 0개    782건 (26%)  ← 진짜 조건 없음. '제한없음'으로 바꿀 후보
└─ 판정축 1개+ 2,179건 (74%)  ← 조건은 있는데 판정 못 함. 그대로 둬야 함
```
- 판별식은 `verdict` 가 **아니라 `scored 축 개수 == 0`** 으로 잡아야 한다(경계가 깨끗함 — 0축인 건 100% 확인필요).
- 74%에 "제한없음"을 붙이면 **거짓 정보**가 된다. 주의.
- 미결정: 문구를 `제한없음` / `조건 없음` / `별도 조건 없음` 중 무엇으로? 추천 점수도 올릴지?
- 적용 위치 2곳: 공고 상세 `match-axes-table.tsx`, AI 추천 카드 배지.

## 3. 미해결 위험 (감사에서 나왔으나 안 고침)

| 위험 | 심각도 | 왜 지금 괜찮은가 |
|---|---|---|
| **localStorage 토큰**(리프레시 포함) | 🟡 | XSS 경로 미발견 + 보안헤더 적용. 근본 해결은 httpOnly 쿠키 — **TLS와 한 세트라 같이 해야 함** |
| **CSP가 Report-Only** | 🟡 | 관찰만 하고 차단 안 함. 전체 페이지 위반 정리 후 강제 전환 (이슈 FE #105) |
| **챗봇 프롬프트 인젝션** | 🟡 | 공고 원문이 프롬프트에 그대로 들어감. **OpenSearch 검색 연동과 같은 변경에서 반드시 함께 수정** |
| **타임아웃 연쇄** | 🟡 | httpx 120초가 DB 커넥션을 붙잡아 외부 지연 시 전체 장애 가능. `/events` 의 불필요한 DB 의존도 함께 |
| **`timed_out`/`_shards.failed` 미검사** | 🟢 | OpenSearch 부분 실패가 200으로 옴. 20회 측정 중 발생 0건 |

### 오판 정정 기록

처음 감사에서 **"백엔드 TLS 부재 → 배포 차단"** 이라고 보고했으나 **틀렸다.**
실제로 확인하니 백엔드는 인터넷에서 접근 불가한 VPC 내부망이고, 프론트는 HTTPS 정상. 설정 파일만 보고 추측한 오판이었다.
**교훈: "암호화 없음" ≠ "위험함". 그 통신이 누구에게 노출되는지가 기준.**

## 4. 에이전트(챗봇) 상태 — 팀원 담당 영역

`bidmate-ai-agent` 를 `PROJECTS/` 에 클론해뒀다.

### 구조 (오해 정정)

"전부 프롬프트"가 아니다. **LLM 호출은 2번뿐**이고 나머지는 결정론적 코드:

```
router(Haiku) → eligibility(코드) → retrieval(코드) → scoring(???) → respond(Sonnet)
```

| 파트 | 줄 수 |
|---|---|
| `tools/search.py` | 586 |
| `tools/bid_info.py` | 252 |
| `tools/eligibility.py` | 168 |
| 프롬프트 | 2개 (router.md, respond.md) |

### 🔴 발견한 문제 2개

**① 백엔드가 옛 버전을 물고 있다**
```
requirements.txt 고정:  589c6ec
에이전트 main:          465b4cc  (6커밋 앞섬)
```
안 쓰이는 팀원 작업: `eligibility tool 수정`, `title 청크 BM25 가점`, **Hotfix 2개**(자격요건 매칭 함수, 신용등급 축).

**② `scoring` 노드가 여전히 스텁**
```python
# run.py
build_graph(router_node, respond_node,
            eligibility_node=eligibility_node,   # 실구현
            retrieval_node=retrieval_node)       # 실구현
            # scoring은 기본값 = stubs.scoring_node ← 하드코딩
```
스텁이 뱉는 **가짜 데이터가 그대로 LLM 프롬프트에 들어간다**:
```
### 자격 매칭도
- R26BK_STUB01: 자격 매칭도 72.0점
  - 실적 여유율 24.0점: 요구 실적 10억 대비 보유 25억, 여유율 2.5배
```
존재하지 않는 공고의 허구 점수를 진짜 데이터 옆에 놓는 것이라, 답변 품질 저하의 유력한 원인.
`intent.type == "full"` 일 때만 타므로 **질문 종류에 따라 갑자기 이상해지는** 증상으로 나타난다.

### 라우터 구조 평가

- 그래프 분기가 **LLM 출력(`intent.type`)에 직결**된다. 다만 구조화 출력(`Literal` enum 강제) + 필터 병합은 코드(`merge.py`)라 통제는 있다.
- 진짜 약점: **오분류 시 복구 장치 없음**, 프롬프트 193줄(Haiku엔 과부하), **라우터 분류 검증 테스트셋 없음**.
- 개선 1순위: **라우터 골든셋**(질의 30개 + 기대 분류).

### 팀원에게 요청할 것

1. `scoring` 실구현 일정. 당장은 **빈 배열 반환으로 바꾸면** 가짜 인용은 막을 수 있음.
2. `465b4cc` 로 버전 올려도 되는지 (Hotfix 2개 미반영 상태).
3. `retrieval` 이 실제 연결됐으므로 **프롬프트 인젝션 경계**(`system` 필드 분리) 필요.

## 5. 인프라 메모

### 배포

```
main 머지 → GitHub Actions → docker build(레이어 캐시) → ECR(SHA 태그)
        → SSM으로 EC2에 명령 → 이미지 pull → Nginx 블루그린 전환
```
- 실측 **약 3분**, 무중단(헬스체크 통과 후 upstream 교체, 실패 시 자동 롤백)
- 이미지 태그가 커밋 SHA라 `/version` 으로 배포본 확인 가능

### 요청 경로

```
사용자 → Nginx(443, TLS 종단·레이트리밋) → Next.js(127.0.0.1 루프백) → FastAPI(10.0.140.134:8000, VPC)
```
평문 구간 2곳은 모두 외부 비노출이라 안전.

### 매칭 사전계산 (`match_results`)

트리거 3개 — `회사 자격 × 공고 요구` 의 곱이라 양쪽 축을 각각 커버:
```
회원정보 수정  → 프로필 훅, 그 회사만 즉시
5분 주기       → 인앱 스케줄러, 새 공고 있을 때만 증분 UPSERT (없으면 DB 미접근)
새벽 1회       → 전체 재계산, 마감 정리 + 증분 누락 보정
```
